# TronIDE v2.3.3 AI Task Runtime Protocol

Status: Accepted for incremental implementation

Baseline date: 2026-07-27

## Release baseline

The provisional v2.3.2 baseline is `origin/release/v2.3.2` at
`f3ba906aaea530bcb79f44beb0e37b56b4148556`. A formal v2.3.2 release tag does
not exist yet, so this document records the branch SHA without creating or
publishing a release tag. The baseline must be updated to the final tag before
v2.3.3 RC0.

The baseline exposes 41 AI workspace tools:

```text
read_current_file, list_open_files, open_file, search_workspace,
create_file, edit_file, undo_last_change, delete_file, rename_file,
read_file, list_files, list_workspaces, create_workspace, switch_workspace,
compile_contract, set_compiler_version, run_static_analysis, run_tests,
git_status, git_diff, git_log, git_stage_all, git_stage, git_commit,
git_create_branch, git_checkout, git_push, git_pull, git_clone,
debug_transaction, list_accounts, get_balance, list_deployable_contracts,
deploy_contract, read_contract, write_contract, check_verification,
prepare_verification, save_recording, replay_recording, export_tronbox
```

Known baseline debt that this protocol is intended to address:

- tools return presentation text instead of one structured result contract;
- the Anthropic tool loop and Chat component own orchestration details;
- progress is visible, but there is no durable task/step state or artifact index;
- confirmations exist, but tools do not share one explicit R0-R3 registry;
- transaction timeout cannot be represented independently from failure.

## Decision

All model adapters, task storage, timeline UI and tool wrappers will share the
vendor-neutral protocol in
`libs/remix-code-reader/src/services/aiTaskProtocol.js`.

### Task and step states

```text
planned -> running -> waiting_for_user -> running -> succeeded
                  \-> failed / cancelled / uncertain
uncertain -> running / succeeded / failed / cancelled
```

`succeeded`, `failed` and `cancelled` are terminal. `uncertain` is deliberately
not terminal because an already-broadcast transaction can later resolve.

### Risk and side effects

| Risk | Side effect | Approval | Automatic retry |
|---|---|---:|---:|
| R0 | none/read-only | no | no by default |
| R1 | local write | yes | never |
| R2 | remote write | yes | never |
| R3 | chain write | yes, plus wallet/mainnet rules | never |

An unknown risk level fails closed and cannot be treated as R0.

### Tool result

```js
{
  ok: boolean,
  code: string,
  summary: string,
  data?: unknown,
  retryable: boolean,
  userAction?: string,
  artifacts: Array<{ type: string, label: string, ref: string }>,
  uncertainty?: string
}
```

The initial adapter accepts legacy string results so existing tools can migrate
incrementally. New runtime code must emit the structured form. The canonical
error set is `INVALID_INPUT`, `NOT_READY`, `NETWORK_UNAVAILABLE`,
`WALLET_LOCKED`, `USER_REJECTED`, `TIMEOUT`, `STATE_CHANGED`, `TX_UNKNOWN`,
`EXECUTION_REVERTED` and `INTERNAL_ERROR`.

## Compatibility and rollout

1. Introduce and test the protocol without changing existing tool execution.
2. Wrap the P0 Golden Workflow tools first.
3. Store versioned task records locally while continuing to read v2.3.2 chat
   history.
4. Move vendor adapters above the canonical runtime rather than copying policy
   or plugin logic into each adapter.
5. Remove legacy string-only handling only in a later schema version after all
   baseline tools have migrated.

### v2.3.3 transaction-intelligence extension

The first extension adds three R0 tools above the 41-tool compatibility
baseline, bringing the v2.3.3 tool belt to 44:

- `get_environment` reports provider, genesis-verified TRON network, wallet
  state and account context; an unknown network remains unknown;
- `preflight_transaction` validates deploy/write context, value, balance, fee
  limit, ABI arguments and the energy estimate when the provider supports it;
- `get_transaction_status` resolves a transaction without resubmitting it,
  briefly polls the same hash while a visible transaction is waiting for its
  receipt, and emits a TronScan link only for an exact known network.

`deploy_contract` and `write_contract` run the same preflight automatically
before their existing confirmation and wallet-signing paths. A preflight
blocker cannot reach a broadcast call. Provider timeouts remain `TX_UNKNOWN`;
the status tool tells the user to query the same hash rather than retrying the
write blindly. Wallet-signing calls keep their plugin and task-runtime queues
open beyond the five-minute udapp deadline, so the wallet method owns the exact
result instead of losing it to an earlier transport timeout. Once an R3 result
is uncertain, the same model response cannot start another chain write.

### Approval and write-lock invariants

- every confirmation displays the registry risk level and side-effect class;
- rejection is the canonical `USER_REJECTED` result rather than a successful
  legacy text response;
- deploy/write approval binds provider, genesis-derived network ID, account,
  value/token fields, fee limit, parameters and compiled-artifact fingerprint;
- udapp recomputes the snapshot at the broadcast boundary and rejects drift;
- Mainnet deploy/write and batch replay require a second explicit confirmation;
- an R1-R3 task acquires one expiring local write lease scoped to workspace,
  branch and (for R3) network/account; other tasks remain read-only until the
  owner finishes or the lease expires;
- approved workspace/branch tools rebind the lease after switching; unrelated
  context drift fails closed with `STATE_CHANGED`;
- normal completion releases the lease. An uncertain side effect keeps a
  three-minute recovery lease, after which crash recovery removes it.

### Vendor tool-protocol invariants

- Anthropic tool-use and OpenAI-compatible function calling are translation
  layers above the same 44-tool registry, task runtime, policy gate and write
  lock; adapters never access workspace, Git, compiler or wallet plugins;
- OpenAI, DeepSeek, Qwen, xAI and an explicitly configured compatible gateway
  share the OpenAI-compatible adapter. A custom gateway must provide its own
  base URL and model ID rather than silently falling through to OpenAI. The
  base URL must include any path prefix required by the gateway (for example,
  `https://gateway.example/v1`); TronIDE does not infer or append that path;
- canonical `input_schema` objects become OpenAI function `parameters` without
  creating a second vendor-specific tool registry;
- prior text turns are carried into both protocols, tool results return to the
  model as protocol-native result messages, and multiple calls in one response
  execute strictly in response order;
- Stop aborts the active request/runtime step, tool iterations are bounded, and
  malformed arguments become structured `INVALID_INPUT` results without
  reaching the executor;
- a model or gateway that rejects tool calling raises an explicit Workspace
  Actions capability error. TronIDE does not run a plain-chat fallback while
  implying that workspace work occurred;
- Google Gemini is a first-class v2.3.3 Workspace Actions vendor. Its native
  tool adapter uses the same 44-tool registry, task runtime, policy gate and
  write lock as the other supported adapters. Providers without a supported
  tool protocol remain chat-only and cannot imply that workspace work occurred;
- an action-required task entry that completes without an accepted Workspace
  Action fails with `MODEL_DID_NOT_CALL_TOOL`; the model's plain-text response
  is not treated as successful execution.

### TRON Skill and Checklist invariants

- the v2.3.3 built-in knowledge pack uses schema
  `tronide.tron-knowledge-pack@1` and contains four declarative Skills
  (`trc20-code-test`, `tronlink-nile-deploy`, `tronscan-verification`, and
  `recorder-tronbox-handoff`) plus the `tron-tvm-security-audit` and
  `energy-bandwidth-optimization` Checklists;
- knowledge items declare objectives, ordered steps or rules, evidence
  requirements, constraints and a canonical-tool allowlist. They contain no
  executable handler, remote download or vendor-specific plugin access;
- side-effecting Skill tools still use the registry's R1-R3 approval, retry and
  write-lock policy. Checklists may allow only R0 tools;
- token workflows read `decimals()` before converting raw supply or balance
  integers; when precision is unavailable they report raw units rather than
  assuming 18 decimals;
- optional Workspace packs load only as bounded JSON below `.tronide/ai/` and
  pass the same schema/tool-policy validation. Missing, malformed, untrusted or
  future-version packs become an unavailable result without disabling built-in
  knowledge, ordinary chat or manual tools;
- Security and Energy/Bandwidth reports whitelist evidence from the selected
  Checklist's tools. A pass or finding without traceable evidence is normalized
  to `needs_review` rather than guessed;
- checklist JSON/Markdown exports contain only structured finding fields and
  redact credential-shaped content while retaining rule IDs, source locations,
  evidence references and remediation.

### Home and Deploy task-entry invariants

- `aiTaskEntries.js` is the versioned, immutable source of truth for four Home
  task cards and five post-deployment choices. Each entry contains a goal,
  recommended Skill/Checklist, expected network, side effects, and TronLink
  prerequisite; it contains no handler or executable model response;
- Home sends only an entry ID and non-secret readiness hints through
  `aiPanel.startTask`. Chat reconstructs the trusted entry prompt and uses its
  existing `onSubmit -> Vendor Adapter -> AITaskRuntime -> Policy Gate` path;
  entry source and ID are recorded in the same local task history;
- missing model/key, disabled Workspace Actions, an unsupported tool protocol,
  an in-flight task, missing TronLink, and a known wrong network return a
  structured visible prerequisite with a recovery action before task
  injection. Unknown network state is verified by the canonical environment
  tool rather than guessed by Home;
- a successful `deploy_contract` produces a structured contract artifact and
  bounded deployment context. Only that runtime success can reveal the next
  step card; model prose is never parsed to infer a deployment;
- receipt explanation, read/write verification, TronScan preparation, Recorder
  saving, and DApp starter generation are buttons. Nothing calls a model,
  signs, writes, or sends until the user chooses one; the chosen goal re-enters
  the same entry protocol and R0-R3 policy path.

### Golden Workflow result invariants

- `aiGoldenWorkflows.js` versions the ordered WF-1 through WF-4 recipes and
  binds each one to exactly one Home entry and built-in Skill. A required phase
  is satisfied only by a successful canonical `step.finished` event for an
  accepted tool in the declared order;
- model prose never counts as evidence. Missing or out-of-order phases produce
  `incomplete`, tool errors produce `failed`, rejected/Stopped tasks produce
  `cancelled`, and `TX_UNKNOWN` or other unresolved chain evidence produces
  `uncertain`;
- WF-2 is read-first: `write_contract` is optional and a rejected optional
  write cannot erase successful compile/deploy/status/read evidence;
- the evaluator produces a bounded, credential-redacted result containing the
  workflow status, passed/required count, per-phase tool summaries, artifacts,
  required result fields, and a recovery or handoff action;
- `task.workflow_result` is persisted inside the existing local task record and
  rendered by the existing task timeline. It is not a second task store or a
  second execution controller;
- WF-4 explicitly points at the external fixed-version TronBox compatibility
  gate. Browser export success alone does not claim CLI compile/test success.

### TronBox handoff compatibility invariants

- the P0 compatibility contract pins Node `20.19.2`, published TronBox `4.8.0`
  and tron-solc `0.8.20`; version drift fails before compilation;
- the runnable fixture is a Recorder deployment plus `Storage.store(42)`. The
  gate invokes the production exporter, validates migration syntax, executes
  both migrations with a deterministic fake deployer, compiles the generated
  contracts with the fixed TronBox version, and verifies ABI/bytecode artifacts;
- CI resolves exactly `tronbox@4.8.0` when an exact local binary is unavailable.
  Both GitHub and GitLab run the gate as blocking work;
- compilation happens in an ephemeral directory with no private key and no
  chain connection. A TronBox compatibility failure blocks WF-4 handoff but
  does not make TronBox a runtime dependency for the browser or WF-1 to WF-3;
- existing exporter fixtures continue to require explicit TODO comments for
  reverted or unconvertible steps rather than silently dropping them.
